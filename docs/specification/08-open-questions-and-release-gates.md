# שערי שחרור, חוסרים והכרעות

זהו אפיון מחקרי גרסה 0.1. מבנה עשיר ובדיקות קישורים אינם אימות דין או תחליף לבדיקת תפעול בשטח. הפרטים להלן אינם מוסתרים מאחורי ״לפי מדיניות״.

| שער | מה נדרש לסגירה | בעל מקצוע/ראיה | יכולת חסומה |
|---|---|---|---|
| G01 | נוסח ניהול ספרים, תוספת ענפית, מסמכים, מספור, שמירה ומועד מס | רו״ח בעל ניסיון באירוח + סעיפים ותאריך | הנפקה עצמית ויצוא המוצג כתואם |
| G02 | חובת רישום תוכנה, קובץ אחיד וסימולטור | רשות המסים/רו״ח + ריצה מאושרת | הכרזת תאימות ישראל |
| G03 | חשבוניות ישראל: API, הרשאות, סירוב, תיקון ומועדים | תיעוד רשמי ו־sandbox | הנפקה הדורשת הקצאה |
| G04 | זכאות תייר ואילת כולל סוג שירות, מקבל וראיות | נוסח חוק/תקנות נוכחי + אישור רו״ח | אפס/פטור אוטומטי |
| G05 | מזומן, תייר, תשלומים, שיקים ופיצול עסקה | הוראה עדכנית + תרחישי רו״ח | מנוע חוקי מחייב במקום בירור |
| G06 | מכר מרחוק/פרונטלי, אוכלוסיות, מניין ימים, מחיר וגילוי | עו״ד צרכנות + טבלת הכרעה מאושרת | חיוב דמי ביטול אוטומטי |
| G07 | מאגר, רמת אבטחה, DPO, דיווח אירוע, העברה לחו״ל ודיוור | יועץ פרטיות/עו״ד + מיפוי נתונים וספקים | פרופיל ציות סופי ושיווק אוטומטי |
| G08 | 7.1א, פנקס אורחים, דרישות רשות ורישוי שירותים | מפרט מלא, רשות מקומית ומפעיל | פתיחת שירות בפרופיל שלא נבדק |
| G09 | נגישות ומהדורת תקן, תחולה, פטור ומסמכים | מורשה נגישות + בדיקות מוצר | הצהרת נגישות סופית |
| G10 | ספק fiscal, סליקה, OTA ומנעולים: חוזים ומקרי קצה | sandbox ותיעוד ספק | חיבור חי וכסף אמיתי |
| G11 | תצפיות משמרת ותרחישי ליבה עם צוות קבלה/כספים/חדרנות | לפחות הרצה מתועדת עם מפעיל לכל פרופיל ראשון | הכרזה שהזרימות אומתו בשטח |
| G12 | אפיון ענפי נוסף לשכר, מטבח, בריכה, נדל״ן ונסיעות | מומחה תחום + חבילת מסכים נוספת | הבטחה שהמודולים האלה שלמים |

## שאלות מוצר שנותרו

יחידת מכירה בסיסית ופרופילים רשאים להשתנות; נדרש חוזה ברור לכל פרופיל: חדר/מיטה/דירה/שעה, תפוסה וחדרנות, משאב בלעדי מול משותף, תעריף לאדם מול ליחידה, תשלום חלקי, מסגרת אשראי, אישורי חריגים, שחזור ויעדי SLA. אלו יכולות ניתנות להגדרה; לא צריך לבחור מלון אחד כדי לאפיין את הליבה. לפני בנייה של פרופיל מסוים צריך לבחור את הערכים, לא להשאיר למפתח להמציא.

הספקים עצמם טרם נבחרו. לכן שמות שדות ספק, קודי שגיאה, זמן timeout, מגבלות rate והתנהגות settlement אינם מוצגים כאן כעובדות. חוזה פונקציונלי קיים ב־06; נספח ספק נדרש לאחר בחירה בשני מסלולי החשבונאות.

## מגבלות פירוט מפורשות

99 המסכים מכסים ליבה רחבה; כל שדה כולל סוג וכלל, וכל פעולה כוללת יעד וכלל ביצוע. מנגנוני חובה, ערכי enum מלאים, תקרות ומדיניות שלא הוגדרו במפורש נשארים הכרעת מוצר לפני בנייה. החוזה הרוחבי מגדיר את רכיבי החיפוש, סינון, pagination, בחירה, שמירה, סגירה וקבצים; הוא אינו טענה שנצפו כל כפתורי OPERA.

אין בחבילה מיפוי מלא לקוד הקיים, אפיון API ברמת schema, תרשים בסיס נתונים פיזי או עיצוב. בדיקת הכיסוי מתייחסת למסמכי האפיון ולא מוכיחה שהפרויקט מממש אותם. המערכת הקיימת לא שונתה במסגרת העבודה הזאת.

## הגדרת השלמה לגרסה שאפשר למסור לבנייה

כל מסך חייב: שדות וערכים סופיים, חובה/תנאי, ברירות מחדל, מקור אמת, הרשאות פעולה, קדם־תנאי, השפעה, כשל ושחזור, יעדי חזרה, תלויות מודול ותרחיש קבלה. כל נושא חוקי פעיל דורש מקור נוכחי וסעיף, הכרעת תחולה ומאשר. כל ספק פעיל דורש נספח וריצת sandbox. בדיקה מבנית ירוקה לבדה אינה מספיקה.

אפשר להעביר כעת למחקר משתמשים ולארכיטקטורת מסכים את חלקי הליבה; מנועי דין, שכר ורישוי אינם מוכנים להטמעה אוטומטית. אין צורך בבעל המוצר שיבדוק כל סעיף לבד: הראיות והחסמים מגדירים בדיוק מה צריך לאמת ולמי למסור.
